EHR Media Intelligence Platform: Write-up

Eyob Simachew · github.com/Eyob-smax/ehr-media-intelligence

A Python pipeline cleans five messy synthetic source layouts (316 patients, 2,126 records) into audited canonical records, maps them to validated FHIR R4 Bundles, writes cited AI summaries, and serves hybrid semantic search (30–90 ms per query) through FastAPI and an accessible Tailwind UI. It has 132 automated tests.

Tradeoffs and why

  • Safety over completeness in identity matching. Two MRNs with the same name and birth date are merged only when the difference looks like a keying error (a transposition or at most two changed digits) and comes from a secondary source. Everything else is flagged for review, because a wrong merge mixes two people's charts while a missed merge only leaves a duplicate.
  • R4B models for R4 output. The required Pydantic v2 stack means fhir.resources 8.x, which ships R5 and R4B, not R4. R4B is backward-compatible for every resource used here. I added my own required-binding and reference-integrity checks because the library accepts invalid status codes and dangling references.
  • MiniLM plus hybrid ranking instead of a clinical embedding model. MiniLM fits the brief and runs well on a CPU, but it misses lay-to-clinical links, so a small auditable synonym table and a 20% keyword score fill the gap. It's transparent but doesn't scale like a terminology service would.
  • Confidence from checks, not from the model. Self-reported LLM confidence is poorly calibrated; grounding checks are deterministic and explainable in the UI. The offline extractive summarizer keeps the system usable without a key and serves as a baseline.
  • Local and simple: SQLite plus Chroma, collection Bundles with deterministic UUIDv5 IDs (reproducible builds and stable cache keys), Tailwind from a CDN with no build step, and no authentication (out of scope). Naive source timestamps are treated as UTC for FHIR instant.

What I'd improve with more time

  • Use a clinical embedding model (e.g. MedCPT) with UMLS/SNOMED synonyms and negation detection: "no hydronephrosis" still counts as a keyword match today.
  • Add HL7 v2 ORU and C-CDA ingestion, plus probabilistic patient matching (Fellegi–Sunter) with a human review queue and name-change history.
  • Evaluate summaries on a clinician-labeled set (per-field precision and recall, omissions), with an LLM-as-judge faithfulness check alongside the lexical checks.
  • Validate against US Core profiles on a HAPI FHIR server ($validate, terminology server); use incremental indexing and async ingestion.
  • For production: authentication and RBAC, access audit logs, PHI controls, and lab trend charts in the UI.

FHIR and clinical concepts I researched

  • DocumentReference (narrative documents) vs DiagnosticReport plus Observation (results); v2-0074 LAB/RAD categories; the v2-0203 MR identifier type.
  • Observation interpretation (H/L/HH/LL/A, HL7 v2 table 0078), dataAbsentReason, valueQuantity.comparator, UCUM units.
  • Bundle reference resolution through urn:uuid fullUrls; required vs extensible bindings; the administrative-gender value set and ISO 5218 numeric codes.
  • LOINC panel and document codes; SI conversions (glucose ×18.016, creatinine ÷88.4, HbA1c IFCC to NGSP).
  • Patient-matching error types: transpositions, namesakes, day/month swaps.

How I validated AI summary quality

  • By construction: structured outputs enforce a schema in which every diagnosis, media item and anomaly cites the record IDs it came from. The prompt asks for chart wording, no inference, and empty lists rather than guesses.
  • On every summary, automatically: cited IDs must exist; every number must appear verbatim in the cited record (wrong numbers are the most dangerous error); key terms must overlap with the cited text; and the 200-word limit is enforced, with one rewrite request and then a deterministic trim. The results set the confidence level, and the problems are stored with the summary and shown in the drawer.
  • Adversarial tests: an injected wrong potassium value, a nonexistent record, an unsupported cancer diagnosis and an uncited claim are all caught. The Claude path is tested with a mocked client: request shape, the shorten retry, refusal, schema mismatch and the auth-failure fallback.
  • Results: all 316 offline summaries pass grounding at ≤154 words. Limitation: these checks are lexical, so they cannot catch omissions or misplaced emphasis, and live Claude output still needs clinician review, which is the first item on my improvement list.
